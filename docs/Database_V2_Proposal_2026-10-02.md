# LabFlow Database Architecture V2 — proposal, 2026-10-02

**Design and migration planning only. No schema, SQL migration, runtime, frontend or operational data changes are made by this document.** Asia/Karachi date. Baseline `development` / `f8f9285`. Read [the evidence and current-model assessment](Database_Architecture_Gap_Analysis_2026-10-02.md) before reviewing this proposal.

## Proposed architecture and scope

Retain PostgreSQL, Prisma 7, `@lms/database`, the Nest modular monolith and one locally authoritative server. Fix the clinical/financial invariants first. A Visit is the actual encounter and clinical order root; Booking is an optional prior request; OrderedTest is each actual test occurrence; Invoice is the financial document. A second generic Order header would duplicate Visit for the present one-order-per-encounter workflow, so it is not proposed.

```text
Tenant → Branch
Patient → Visit ← optional confirmed Booking ← BookingItem requests
           ├─ OrderedTest → immutable TestVersion → parameters/choices/ranges
           │    ├─ SampleTest → Sample (one physical container) → SampleEvent
           │    └─ Result revisions → ResultValue snapshots
           ├─ Invoice → InvoiceLine → Payment / InvoiceAdjustment
           │                       └─ DoctorShare → DoctorShareSettlement
           └─ Report → ReportVersion → ReportVersionResult → exact Result revision
                                     └─ ReportEvent / local PDF artifact metadata
Significant transaction → AuditLog + durable Notification / future SyncOutbox
Future cloud request → SyncInbox → review → local Booking; website never → LAN/DB
```

The full staged target has **47 models: 29 retained/reworked + 18 additions**, including dormant corporate and future bridge structures. This is an inventory, **not a demand to add 18 tables in one migration**. First clinical phase adds Visit, OrderedTest, TestVersion, PackageVersion, SampleTest, SampleEvent, ReportVersion, ReportVersionResult and ReportEvent; identifier/idempotency support follows the relevant workflow. Finance, sessions, notification attempts and inbound bridge are separate acceptance phases. Existing dormant Company/PatientCompany remain dormant. SyncInbox and outbox extensions are deferred until a bridge is authorized. Standalone Employee, generalized Role/Permission tables and CommissionRule are not baseline V2 requirements.

## Model conventions — apply to every card below

“Existing” keeps its existing TEXT CUID primary key and table mapping; **do not rekey historical data**. “New” uses a TEXT cryptographically generated UUID string primary key, except IdentifierCounter's natural composite PK. Keeping IDs as TEXT lets new/old IDs coexist without a mass FK conversion. UUID is internal identity, not a human accession number or a secret. PKs are globally unique within their table.

Domain roots require Tenant FK; operational roots require Branch FK. Child tables inherit ownership through required parent relations; selected composite keys/FKs carry tenant/visit/definition scope where necessary to prevent crossed links. Parent identity `(tenantId,id)` and encounter identity `(tenantId,branchId,visitId)` must be backed by nonpartial unique keys before FK use. Do not redundantly add tenant indexes when an existing leftmost composite index already serves the query. All actual required FK columns need either an existing appropriate left-prefix index or a measured candidate in the index plan.

Each card names business uniques (U), additional query indexes (I), important FKs and lifecycle. PK indexes are implicit; no extra index if I says “U covers lookup.” Mutable masters/drafts get createdAt, updatedAt and an integer rowVersion for optimistic edits. Events get occurredAt and recordedAt; immutable revisions get createdAt and approval/release metadata, without pretending updatedAt is a history log. Instants are `timestamptz(3)`; clinical DOB is DATE. Currency amounts remain Decimal(12,2) PKR and measured values initially Decimal(16,6), subject to lab precision approval. Actors reference deactivated retained User records; historical actor display snapshots survive renaming.

FK deletion defaults for V2: **RESTRICT clinical/financial/provenance parents**, even where today's optional relation uses SET NULL. Deactivate masters. Hard-delete only never-used drafts under an authorized maintenance path, with safe child cleanup; do not cascade from issued/released records. “Append-only” means application authorization plus a database privilege/guard policy, not a comment. The global timezone conversion and integrity-key additions may touch otherwise unchanged good model shapes in a later authorized migration.

Clinical definition versioning is independent of live price edits: issuing an invoice snapshots its price; no extra price-history table is needed just to keep historic bills correct. Panel = one TestVersion with multiple parameters, not automatically a Package. Simple packages contain direct tests in the baseline. Nested packages are not exposed as working today; defer authoring them. If later required, add a real scoped child-PackageVersion FK, exactly-one-target check, a locked acyclic publication check and finite flattening limit, then freeze the expanded result. Never recurse blindly through current composition.

At checkout expand the **selected published composition once** into OrderedTests, in the same transaction as invoice issue. One package InvoiceLine can fund many OrderedTests. Quantity creates explicit occurrences. Reject overlap between direct/package/member selections unless staff explicitly confirms repeat work and reason; do not silently double-charge or collapse intentional repeats. Each occurrence has one origin; current clinical readiness compares its own state/current approved result, not catalog test ID sets. Owner must approve commercial pricing/allocation if overlapping bundles should instead share work.

**Range publication/selection contract:** clinician approves units, bounds, applicability and age policy. Reject negative or inverted age bounds, inverted normal/critical bounds and incompatible units. Every parameter's range set uses one explicit age unit, with half-open age intervals; whole calendar months/years are computed using approved calendar rules, days from clinical dates. Do not convert legacy months by multiplying by 30. Unknown DOB/clinical sex cannot satisfy a specific range; only an approved universal/unbounded fallback may apply, otherwise hold for authorized review. First filter eligible age/sex/definition/method context, then exact-sex versus universal fallback according to explicit policy; zero or multiple equal-applicability matches is not NORMAL. Reference text/interpretation can accompany numeric bounds without inventing a medical threshold.

Overlapping equal-applicability intervals are rejected on **publication under the parent TestVersion lock**, making concurrent range edits serialize. Explicit universal fallback may overlap a specific-sex policy only under approved precedence; the database CHECK cannot compare sibling rows. Native exclusion constraints are optional after profiling/requirements, not an automatic `btree_gist` extension dependency. Pregnancy, analyzer protocols and instrument registries are future requirements; do not pretend the current Gender enum or a birth-date estimate supplies those clinical facts.

**Release contract:** validate Sample acceptance, SampleTest assignment, same encounter/order/version and actor permission; enforce all required values, typed choices/boolean/numeric scale and approved evaluation context. Acquire OrderedTest/Visit locks in consistent order and check rowVersion/state. Release Result, freeze values, build ReportVersion membership when eligible, record AuditLog and queue intent atomically. No HTTP/SMS/PDF rendering inside that transaction. A two-person verification policy is optional owner/clinical configuration; actor/time fields support it without a sprawling status enum.

**Correction contract:** released Result v1 remains unchanged; create DRAFT v2 with previousResultId, reason and actor, copying relevant values/context. Existing released report remains the historical v1; mark current availability pending/withdrawn if clinically required by policy, do not silently continue distributing known incorrect data. Review/release v2 atomically supersedes current result, creates ReportVersion v2 referencing exact revisions, and updates current pointers. A result amendment can preserve other unchanged test revisions. Revoke outdated online access where possible and publish v2 readiness with a new event ID. Previously printed v1 cannot be recalled electronically; retain delivery history and contact recipients according to clinical policy.

This is a **small ledger-like movement model**, not general accounting. Initially each Payment belongs to one Invoice: no multi-invoice PaymentAllocation table without corporate settlement requirements. Preserve existing amounts and sale snapshots. Define unitPrice as **base charged unit price before line discount** for compatibility (or rename only after API compatibility); lineTotal = quantity × unitPrice − lineDiscount + lineTax. Store original price and actual discount distinctly. Tax remains zero unless owner supplies an applicable policy; no tax law is assumed here.

Define netCharge = original grandTotal + debits − credits − write-offs (with adjustment reversals). Define netReceipts = receipts − refunds − receipt reversals. Raw balance = netCharge − netReceipts; `amountDue=max(rawBalance,0)`, customer credit `max(-rawBalance,0)`. Caches are updated under Invoice lock and independently reconcilable from immutable entries. A refund by itself can reopen debt; cancellation refund pairs with a credit/void adjustment according to authorized business policy. Never clamp away an unrecorded overpayment. Cap refund sum at attributable receipt value under lock. A paid issued invoice is retained even when its net charge is credited to zero.

Payment operation transaction: claim OperationRequest, lock Invoice (and CASH shift in consistent order), reread balances/status, enforce amount and method, append movement, recompute Decimal caches/state, append AuditLog and commit. Same key+same input returns prior result; same key+different input rejects. Two different receipt requests compete against the current locked balance. Issuance/conversion similarly locks Booking/Visit and preserves uniqueness.

Cash expected = openingFloat + attributed CASH receipts − attributed CASH refunds/reversals. Doctor payouts and miscellaneous expenses are **not implicitly included**: if owner wants those from the same drawer, represent explicitly attributable authorized cash movements in an additional approved phase; do not hide them in shift notes. Close locks the shift and disallows new attributed receipts; all money writers acquire that shift lock before posting. A receipt belongs to one shift, not two overlapping inclusive time windows. Preserve snapshot expected/count/variance and who closed it.

Commission basis/eligibility is an owner decision: current percentage-of-grandTotal is preserved until approved change; fixed invoice rule creates an invoice-level contribution; per-test fixed creates one per actual OrderedTest occurrence, including package tests only after explicit policy. Package discount allocations must sum exactly to billed line total with a documented residual rounding rule. Earned, payable, paid and reversed are different amounts/states; do not sum reversal rows as new earnings. Partial cancellation/refund uses approved pro-rata or per-work policy and cannot silently change original earned values. No CommissionRule registry is required for the current doctor-level defaults because contribution snapshots already retain history.

Every approved business mutation and relevant local intent share a transaction with audit. Notification delivery and bridge workers are separate background work inside the modular application/optional agent, not microservices. Claim a bounded batch using short lock+lease transactions; send outside transaction; persist outcome using claim token. One worker is enough initially, conditional leases still permit safe restarts. Retry exponential backoff with jitter, max attempts and actionable abandonment. Recheck consent/current report release before sending. Template/provider snapshots make retries independent of today's settings. Provider acceptance is not confirmed delivery.

Exactly-once external SMS delivery cannot be promised: crash after provider acceptance and before local recording is ambiguous. Use provider idempotency when supported; otherwise record unknown outcome and reconcile before a blind resend. Local unique intent prevents duplicate requests, not this remote ambiguity. Do not run a provider call in a clinical transaction or make clinical success depend on its completion.

Sync is at least once with atomic inbox dedupe + local import. Local owns patients, actual orders, prices, samples, results, reports and financial state. Cloud owns unaccepted booking requests/public website content. After local acceptance, newer online edits become review requests, not last-write-wins overwrites. Track source version/ETag; reject stale updates, quarantine gaps/conflicts, and acknowledge durable receipt independently of clinical acceptance. A future approved outbound snapshot contains only required readiness/tracking/released report metadata or explicitly authorized content. Payment/public eligibility changes emit versioned withdrawal/update events. A bridge outage can leave stale online availability; define expiry and safe withdrawal policy before patient access goes live. No local secrets, full audit stream or whole operational DB replication.

Restore must not blindly replay accepted outbox messages. Stable event IDs and cloud dedupe survive restoration; reconcile with remote acknowledgement and current aggregate version, publish current withdrawal/version state, and rotate/revoke sessions where appropriate. Restored local human counters never reuse a number already externally issued; compare maxima/exported ranges before reopening operations. Multiple independent branch writers require site-prefixed identifiers and explicit authority; not part of this single-server deployment.

## Keep, modify, add and deprecate

**Keep good structures:** Tenant, FeatureFlag and SmsTemplate business shape; dormant Company structure; existing Decimal prices/values and invoice-line snapshots; doctor-rule snapshots; stable CUID IDs/table mappings; existing TestParameterChoice rows and normalized Result/ResultValue separation; required FKs; centralized permissions; singleton owned PrismaPg pool. No changes merely for naming fashion.

**Modify:** Branch/User/Patient scope and revocation/identity, PatientCompany scoped pair, Test/parameters/ranges and Package/items for versioned definitions, Booking for structured requests, Invoice/line for Visit ownership, Payment/Shift for attributable movements, Sample for specimen/work lineage, Result/Value for immutable revisions/context, Report for exact version membership, DoctorShare for contributions, Notification for durable claims, AuditLog for actual evidence, Configuration for explicit scope/type. ## Identifier strategy

| Identifier | Proposed strategy / scope / recovery |
|---|---|
| Existing internal patient/other PK | Retain CUID TEXT exactly; never expose PK as authorization secret |
| New model/internal/event IDs | Crypto UUID TEXT; unique constraint, collision error handled; no database-wide rekey |
| Patient LAB/MRC | Preserve current tenant-unique permanent values; atomic counter namespace per identifier, optional manual MRC uniqueness; owner approves meaning before any branch/visit reinterpretation |
| Visit accession | Separate tenant-unique human sequence, branch prefix if future independent sites; business-day prefix uses Asia/Karachi |
| Invoice / Booking / Sample / Report number | Atomic IdentifierCounter increment+return inside relevant transaction; namespace/scope/day explicit; retain tenant unique constraint; bounded transaction retry on conflict |
| Public tracking token | Crypto random ≥128 bits, tenant-scoped lookup and secondary verification later; old tracking IDs remain aliases until sunset approved; uniqueness retry; rate limits outside local DB |
| Sync event / operation key | Stable crypto ID generated once, persisted before reuse; unique dedupe keys; never regenerate on transport retry |

Counter allocation is one atomic update/upsert under lock, not count()+findFirst(). Initialize above the maximum parsed **valid existing** suffix in each namespace; preserve malformed/manual numbers as reserved aliases and review exceptions. Check restored maxima against issued records. Gaps are acceptable; “gapless” legal numbering is not inferred. Workstations use server allocation while internet is absent; they cannot independently create authoritative visits if the local server is down.

## State machines and timestamps

| Aggregate | Allowed lifecycle and guards |
|---|---|
| Booking | PENDING_REVIEW → CONFIRMED → ARRIVED → CONVERTED; pre-conversion CANCELLED/EXPIRED explicit actor/reason/time; rebook new request |
| Visit / OrderedTest | Visit OPEN → IN_PROGRESS → COMPLETED, or CANCELLED with reconciliation; work ORDERED → AWAITING_SAMPLE → IN_PROGRESS → RESULT_RELEASED, or CANCELLED; completed clinical work is corrected, not silently reopened |
| Sample | PENDING_COLLECTION → COLLECTED → optional IN_TRANSIT → RECEIVED → ACCEPTED → IN_TESTING → COMPLETED → DISCARDED; RECEIVED → REJECTED; recollection creates new Sample pointing to rejected one |
| Result revision | DRAFT → RELEASED after validation; old RELEASED → SUPERSEDED when new revision released; authorized VOIDED with retained content/reason; edit draft uses rowVersion |
| Report / version | Report readiness NONE/PARTIAL/READY derived from required ordered work; version DRAFT → APPROVED → RELEASED → optional WITHDRAWN/SUPERSEDED; print/download/delivery are separate events; archived metadata orthogonal |
| Invoice | DRAFT → ISSUED → SETTLED based on reconciled balance; authorized credit/void retains issued record; later debit/refund may reopen financial balance; unpaid/partial/paid derived numerically |
| Payment | Local posted movement is SETTLED and immutable; optional future provider intent PENDING → SETTLED/FAILED/CANCELLED kept separate from invoice paid state; refund/reversal new movement |
| Cash shift / commission | Shift OPEN → CLOSED under lock; share earned/payable/settled/reversed projections from contributions/settlements, not edits of historic amounts |
| Notification | QUEUED → SENDING(lease) → ACCEPTED → DELIVERED when confirmed; failure RETRY_WAIT → SENDING or ABANDONED; ambiguous outcome held for reconciliation; suppressed consent not sent |
| Sync | QUEUED → IN_FLIGHT(lease) → ACKNOWLEDGED; transient RETRY_WAIT, permanent QUARANTINED/ABANDONED; inbox RECEIVED → IMPORTED/CONFLICT/REJECTED; ack != clinical acceptance |

These are design vocabularies, not requested enum edits. Preserve old values through compatibility mapping. Record occurred/recorded/released/cancelled/approved/closed separately. Report READY is completeness, APPROVED is clinical authorization, RELEASED is issued content, PRINTED is evidence of printing if explicitly confirmed, DELIVERED is handover/access evidence. None should be inferred from payment alone.

## Proposed constraint plan

| Guarantee | Mechanism / priority |
|---|---|
| Shared organization/encounter/definition | Scoped composite unique identities and FKs for Visit, work, sample assignment, result parameter/version and report membership; P0/P1. Some business state still requires locked service checks |
| Exactly one catalog sale/request target | CHECK XOR testId/packageId for InvoiceLine/BookingItem; PackageItem direct TestVersion required; P1 |
| Amounts/quantity | CHECK quantity integer >0, amounts ≥0, receipt amount >0; discount ≤ base extended charge; line/formula and invoice-header formula; validate round/scale policy; P1 |
| Range bounds/context | CHECK nonnegative age, lower<exclusive upper, compatible normal/critical order, controlled units/types; overlap publication serialized under parent lock; P0 |
| Typed result value | CHECK mutually exclusive type fields with nonnull actual value; choice FK/key or release membership validation; required parameter completeness evaluated under work/definition lock; P0 |
| Active result/shift | Partial unique one RELEASED and one DRAFT per work, one OPEN per tenant/branch/drawer; NULL branch prohibited for live shifts; P0/P1 |
| Provenance | Required release actor/time, amendment predecessor/reason, settlement original reference; FK RESTRICT plus deactivation; P0/P1 |
| Idempotency/revisions | Unique operation keys/event IDs, parent/revision, current pointers to own aggregate; conflicting retries fail; P1/P4 |
| Lifecycle/time | CHECK closed shift requires closer/time/count; released revision requires actor/time; timestamp order where valid; occurredAt can precede recordedAt without forcing false equality; P1 |
| Balance/commission sums | Locked transaction + reconciliation tests/jobs; **not** a cross-row CHECK; P1 |
| Immutability | Runtime role denied audit UPDATE/DELETE; narrowly reviewed guard triggers for released Result/values and approved report membership/content where DB enforcement is needed; maintenance separately authorized and audited; P0/P1 |

CHECK passes NULL unless explicitly addressed: pair with NOT NULL or a null-combination predicate. Do not claim one CHECK can enforce required sibling parameters, package acyclicity, total refunds or sum of invoice lines. DB constraints protect direct SQL as well as Prisma; state and clinical authority remain domain responsibilities.

Concrete context keys to review in the future schema: SampleTest carries visitId with `(visitId,sampleId)` → Sample and `(visitId,orderedTestId)` → OrderedTest. Result references the assignment tuple `(sampleTestId,sampleId,orderedTestId)` and carries visitId/testVersionId consistent with OrderedTest. ResultValue carries testVersionId with `(testVersionId,resultId)` → Result and `(testVersionId,testParameterId)` → TestParameter; a selected range must reference that same parameter. ReportVersionResult carries visitId with scoped FKs to its ReportVersion and Result, and the work identity agrees with the result. Required supporting unique tuples are explicit integrity keys, not substitutes for the existing primary keys. Current-version/predecessor pointers similarly reference their own aggregate; application locks enforce publication and predecessor ordering. These are design requirements, not SQL applied in this phase.

## Deletion, retention, backups and settings

| Entity family | Policy |
|---|---|
| Organization/branch/user/patient/referrer/catalog | Deactivate; merged patient retains alias/tombstone and audit; no deleting an actor to erase provenance |
| Booking/Visit/OrderedTest | Cancel with actor/time/reason; retain ordered history and financial reconciliation |
| Catalog versions/choices/ranges/package members | Published immutable, restrict if referenced; draft hard delete only unused |
| Specimen/events | Dispose physical material according to lab policy, retain digital custody/recollection record |
| Released results/report versions/artifacts | Immutable history, amendment/withdrawal, legal/clinical retention and authorized export; no cascade |
| Issued invoices/lines/receipts/adjustments/shares/settlements/shifts | Retain; reverse/credit, never destructive correction |
| Audit | Append-only restricted access; approved archival/export; no broad UI logging |
| Notification/integration envelopes and attempts | Purpose-bounded sensitive data retention; retain durable dedupe identity even after payload expiration |
| Sessions/security attempts | Expire/revoke; purge after approved security retention, never backup reusable raw tokens |
| Settings | Audited edits; immutable clinical/report snapshots retain applicable policy; deployment secrets external |

Owner/clinical/legal advisers set actual Pakistan record periods, access/export rules, consent purpose and disposal policy; no arbitrary seven-year rule is invented. Minors may have guardian-owned shared contact and no CNIC. Consent latest state is purpose/channel/contact aware; legacy true becomes **legacy/unverified evidence**, not a fabricated fresh opt-in. Patient merge locks both identities, requires human verification, records old→new identity and immutable event, preserves report identity snapshots and old accession lookup; avoid bulk rewriting released record identities.

Backups: transaction-consistent pg_dump plus a manifest of immutable artifact keys/hashes/template/schema/app versions; copy matching PDFs, secrets/key recovery through a separate protected mechanism, verify hashes and restore into isolated PostgreSQL before upgrade. If point-in-time recovery is required, plan WAL archiving/base backups **and compatible file retention**, not merely a Backup table. Restore tests cover schema/application compatibility, external event reconciliation and counter maxima. Use independent/offline copies against drive failure/ransomware, UPS and documented recovery procedure. RPO/RTO/frequency/retention require owner approval. No backup subsystem implemented here.

File protocol: ReportVersion starts artifact PENDING; render from frozen data to a temporary local file, hash, durably rename under stable relative storage root/key, then record READY/hash/size/generatedAt conditionally. File failure leaves retriable artifact state; business release remains recorded and delivery withheld until artifact ready. Reconcile orphan/pending/missing files. A regenerated missing file must match approved content/template; if exact reproduction differs, record replacement artifact/version rather than silently replacing an issued PDF. No large PDFs in PostgreSQL and no machine-specific absolute path as portable identity.

Settings: bounded typed JSON for branding/print/feature policy; relational clinical definitions and financial records; explicit tenant/branch scope; credentials only environment/protected server store with secret references. Save branding+organization name+audit atomically. Preserve versioned lab header/print template in issued output. Offline production bundle must include required browser/fonts/assets and run without remote logo/font dependence; do not treat current development packaging as certified deployment.

## Prisma 7 and PostgreSQL implementation considerations

Stay on exact Prisma CLI/client/adapter **7.10.0**, pg 8.23.1 and `packages/database/prisma7.config.ts`; generated client/public package facade and single owned pool remain. No Prisma 8 config/package or new adapter is needed. Use checked relation inputs, Decimal values, named composite keys and interactive transactions with explicit locking or isolation/retry; P2002 uniqueness and P2034 transaction conflicts are handled deliberately, not arbitrary infinite retries. PostgreSQL default isolation does not fix reads made outside a transaction. Keep transactions short, with no renderer/network waits. Existing RSS increase remains documented (~112–124 MiB versus ~51 MiB), with no new leak/duplicate-client evidence or memory-only redesign.

Some PostgreSQL checks/partial constraints/native immutability guards need reviewed SQL beyond Prisma schema representation. Maintain versioned native-DDL expectations and catalog regression checks, so introspection/diff does not silently discard protections. Do not use preview features or unsupported resolutions merely to encode a constraint. [Prisma 7 feature matrix](https://docs.prisma.io/docs/orm/v7/reference/database-features), [transaction guidance](https://docs.prisma.io/docs/orm/v7/prisma-client/queries/transactions).

PostgreSQL row locks/Serializable, conditional updates, partial unique indexes, native FKs/CHECK and short leased queue claims are appropriate. A cross-row aggregate is not a CHECK, and NULL semantics must be explicit. Exclusion constraints or pg_trgm are optional justified extensions, not baseline requirements. Date versus instant migration must state the original timezone interpretation. [PostgreSQL 18 constraints](https://www.postgresql.org/docs/18/ddl-constraints.html), [date/time types](https://www.postgresql.org/docs/18/datatype-datetime.html).

The current resolved production dependency closure still contains Prisma CLI-origin advisory packages via the client's optional Prisma peer; the prior hardening document distinguishes installed closure from the exercised PostgreSQL runtime query path. V2 design does not remediate or relabel those findings. See [Prisma 7 migration and hardening evidence](Prisma_7_Migration_2026-10-02.md).

## Explicitly not recommended

No database reset, mass UUID rekey, enterprise 200-table LIS, generic EAV, mutable Visit JSON, event sourcing of every entity, Kafka/microservices/CQRS, premature FHIR/HL7/analyzer protocol, full accounting ERP, distributed consensus, per-workstation authoritative databases, immediate SaaS RLS/control-plane build, forced dependency overrides, direct public website access to local systems, guessed clinical ranges/legal retention, or silently “corrected” old financial/medical facts. Do not add indexes to every column, convert all numeric values to float, or use immutable audit JSON as a substitute for actual report/result versions.

## Owner and clinical decisions before implementation

1. Confirm LAB/MRC meaning and permanent versus visit accession policy; keep current identifiers valid.
2. Clinical lead approves age units/boundaries, unknown/estimated DOB/sex handling, range/method/unit policies, required values, critical review, authorized release and optional second approver.
3. Approve duplicate/package/repeat behavior, whether any work can be shared across billed bundles, cancellation coverage and package share-price allocation.
4. Approve partial report issuance, release versus payment policy, archived access, amendment withdrawal/notification and delivery verification.
5. Approve commission basis/eligibility, package/quantity counting, payout timing and refund/clawback rules; retain current historical calculations.
6. Approve refund, credit, write-off and overpayment policies; cash drawer users/float and whether expenses/doctor payouts belong in drawer scope.
7. Approve patient dedupe/merge authority, guardian contacts, CNIC verification and consent purpose/history; avoid invented opt-in.
8. Approve actual clinical/financial/audit retention, export/access policy, backup RPO/RTO/storage and restore drill responsibilities with appropriate local advisers.
9. Confirm branch visibility policy for owner/operator detail reads, future non-login employees and extra role activation only when needed.
10. Authorize bridge scope/published data/verifier/expiry/conflict ownership separately; authorize staged implementation only after this documentation review.

These decisions do not block this completed investigation; they gate future schema/runtime work. No implementation approval is requested or inferred by creation of this proposal.
